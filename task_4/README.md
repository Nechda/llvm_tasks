# Задание 4 — скалярный ASM → LLVM IR

В [ISA.md](ISA.md) описаны набор инструкций и его обоснование по статистике.
[app.asm](app.asm) реализует полную симуляцию воды из `task_1/app_Os.ir`:
инициализацию, периодические граничные условия, двойную буферизацию, поиск
диапазона высот и отрисовку пикселей. Векторных инструкций и вызовов подпрограмм
в ASM нет. `pixel` и `flush` — самостоятельные инструкции.

## Сборка и запуск

SDL и репозиторий `llvm_course` не требуются. Должны быть доступны компоненты
LLVM Core, ExecutionEngine, MCJIT и поддержка целевой архитектуры текущей машины.
Пример с используемым здесь каталогом сборки LLVM:

```bash
cmake -S task_4 -B build/task_4 \
  -DLLVM_DIR="$HOME/github/llvm-project/build/lib/cmake/llvm" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build/task_4 -j4

# Прямые IR-эквиваленты и запуск через MCJIT Execution Engine:
build/task_4/asm2ir task_4/app.asm build/task_4/direct.ll --direct --run --frames 3

# Вызовы эмуляторов инструкций, кроме управления потоком:
build/task_4/asm2ir task_4/app.asm build/task_4/calls.ll --calls --run --frames 3

# Стандартная оптимизация LLVM уровня O2 перед сохранением и запуском IR:
build/task_4/asm2ir task_4/app.asm build/task_4/optimized.ll --direct --opt --run --frames 3

# Только восстановление графа потока управления (CFG), без реализации вычислений:
build/task_4/asm2ir task_4/app.asm build/task_4/cfg.ll --cfg

# Чистая симуляция: без линковки с LLVM и без генерации IR:
build/task_4/asm_sim task_4/app.asm --frames 3

cmake --build build/task_4 --target task4_check
```

Если MCJIT ещё не собран в каталоге сборки LLVM:
`cmake --build ~/github/llvm-project/build --target LLVMMCJIT -j4`.
Установленный LLVM можно выбрать через `-DLLVM_DIR="$(llvm-config --cmakedir)"`.

При `--run` путь выходного файла необязателен. Без `--run` программа только
генерирует и проверяет IR. `--frames N` переопределяет значение `.const FRAMES`;
иначе программа на ASM выполняет все 20 000 кадров.

Флаг `--opt` включает `PassBuilder::buildPerModuleDefaultPipeline(OptimizationLevel::O2)`:
стандартную последовательность оптимизирующих проходов нового менеджера проходов
LLVM с зарегистрированными анализами и связями между менеджерами анализов.
Оптимизация применяется к сгенерированному модулю до сохранения и исполнения
через Execution Engine; `verifyModule` вызывается до и после оптимизации.
Флаг работает с `--direct` и `--calls`. Без него IR сохраняется в исходном
сгенерированном виде.

## Запуск с настоящей графикой SDL

Для графики нужны установленная библиотека SDL2 с заголовочными файлами
(в Ubuntu/Debian — пакет `libsdl2-dev`) и репозиторий курса `llvm_course`
с файлом `SDL/sim.c`. Конфигурация `TASK4_USE_SDL=ON` заменяет заглушки на
этот файл и линкует оба исполняемых файла с SDL2:

```bash
cmake -S task_4 -B build/task_4_sdl \
  -DLLVM_DIR="$HOME/github/llvm-project/build/lib/cmake/llvm" \
  -DCMAKE_BUILD_TYPE=Release \
  -DTASK4_USE_SDL=ON \
  -DLLVM_COURSE_ROOT="$HOME/github/llvm_course"
cmake --build build/task_4_sdl -j4

# Прямой IR с оптимизацией и запуск через Execution Engine:
build/task_4_sdl/asm2ir task_4/app.asm --direct --opt --run --frames 100

# IR с вызовами эмуляторов инструкций:
build/task_4_sdl/asm2ir task_4/app.asm --calls --run --frames 100

# Чистая эмуляция ASM:
build/task_4_sdl/asm_sim task_4/app.asm --frames 100
```

Путь `LLVM_COURSE_ROOT` нужно заменить на расположение своего репозитория курса.
Если CMake не находит нестандартную установку SDL2, можно передать
`-DSDL2_DIR=/путь/к/каталогу/с/SDL2Config.cmake`.

Из курса подключается только `sim.c`: `simInit` и `simExit` вызываются нашими
программами, поэтому `start.c` не нужен. В режиме `--direct` Execution Engine
сопоставляет символы `simPutPixel` и `simFlush` с реальными функциями SDL-обёртки;
в режиме `--calls` и в симуляторе их вызывают функции-эмуляторы. Завершение окна,
включая возможное ожидание его закрытия, определяется `simExit` из курса.

Контрольные суммы печатают именно заглушки, поэтому для сравнения хэшей
используется отдельная сборка `build/task_4` с `TASK4_USE_SDL=OFF` (по умолчанию).
Проверки `task4_check` доступны только в такой конфигурации.

## Сохранённый IR

В репозитории лежат два модуля, полученных из `app.asm` с помощью LLVM 24:

- [app.ll](app.ll) — прямые IR-эквиваленты инструкций ASM без оптимизации;
- [app_optimized.ll](app_optimized.ll) — тот же модуль после стандартного
  оптимизирующего пайплайна `O2`.

Оба файла содержат полное приложение с исходным лимитом **20 000 кадров**.
Для повторной генерации из корня репозитория:

```bash
build/task_4/asm2ir task_4/app.asm task_4/app.ll --direct
build/task_4/asm2ir task_4/app.asm task_4/app_optimized.ll --direct --opt
```

## Сравнение хэшей в разных режимах

Все команды ниже выполняются из корня репозитория после сборки. Каждый запуск
исполняет **три кадра** и печатает контрольную сумму после каждого кадра:

| Режим | Команда и смысл |
| --- | --- |
| Прямое исполнение | `asm2ir --direct --run`: ASM преобразуется в операции LLVM IR, MCJIT компилирует их в машинный код и запускает через Execution Engine |
| Прямое исполнение с оптимизацией | То же с `--opt`: перед компиляцией выполняется стандартный пайплайн `O2` |
| Эмуляция инструкций через IR | `asm2ir --calls --run`: машинный код вызывает эмулятор для каждой инструкции, кроме управления потоком |
| Эмуляция инструкций через оптимизированный IR | То же с `--opt` |
| Чистая эмуляция | `asm_sim`: Visitor исполняет ASM через функции-эмуляторы, без генерации IR и без Execution Engine |

Вывод заглушек можно одновременно увидеть в терминале и сохранить в файлы:

```bash
build/task_4/asm2ir task_4/app.asm --direct --run --frames 3 | tee build/task_4/direct.txt
build/task_4/asm2ir task_4/app.asm --direct --opt --run --frames 3 | tee build/task_4/direct_opt.txt
build/task_4/asm2ir task_4/app.asm --calls --run --frames 3 | tee build/task_4/calls.txt
build/task_4/asm2ir task_4/app.asm --calls --opt --run --frames 3 | tee build/task_4/calls_opt.txt
build/task_4/asm_sim task_4/app.asm --frames 3 | tee build/task_4/simulator.txt
```

Ожидаемый вывод каждого запуска:

```text
[stub] frame=1 pixels=1179648 checksum=ecf6ae8acb2327e0
[stub] frame=2 pixels=2359296 checksum=7c3c891ae0faf7f9
[stub] frame=3 pixels=3538944 checksum=66bca24457862d80
[stub] finished: frames=3 pixels=3538944
```

Строка `instructions=153 blocks=21 registers=71` выводится `asm2ir` отдельно
в стандартный поток ошибок и в эти файлы не попадает. Контрольная сумма
накопительная: она учитывает цвета всех пикселей от начала исполнения.

Проверка точного совпадения вывода, включая хэши всех трёх кадров:

```bash
cmp build/task_4/direct.txt build/task_4/direct_opt.txt &&
cmp build/task_4/direct.txt build/task_4/calls.txt &&
cmp build/task_4/direct.txt build/task_4/calls_opt.txt &&
cmp build/task_4/direct.txt build/task_4/simulator.txt
```

Если весь вывод совпадает, команда завершается с кодом 0 без сообщений.
Для автоматической проверки с дополнительным сравнением с исходным
`task_1/app_Os.ir`:

```bash
cmake --build build/task_4 --target task4_check
```

## Структура

- `instructions.def` — общая для парсера и реестра эмуляторов таблица кодов
  операций, их текстовых имён и сигнатур операндов.
- `ensure.h` — общие проверки `ENSURE(expr)` и `ENSURE_MSG(expr, message)`.
  При нарушении условия они бросают `std::runtime_error` с выражением, именем
  файла и номером строки C++; второй вариант также добавляет пояснение.
  Условие вычисляется один раз, пояснение — только при ошибке.
- `asm.{h,cpp}` — типизированные операнды, парсер, базовые блоки, разрешение меток
  и интерфейс чтения инструкций `Visitor`. Сообщения об ошибках содержат номера
  строк исходного ASM. Директивы должны предшествовать их использованию;
  значения констант задаются литералами.
- `ir.cpp` — трёхпроходный ASM2IR. Сначала создаются все базовые блоки ASM,
  затем в отдельном входном блоке выделяется память для обнаруженных регистров
  и буферов, после чего инструкции преобразуются через `Visitor`.
  Обёртка `Arguments` подготавливает исходные значения `Value` до записи
  результата, в том числе при совпадении исходного и целевого регистров.
- В режиме `--direct` обработчик `switch` возвращает сгенерированное значение
  `Value`. `fill.f32` разворачивается в отдельный цикл IR; остальная структура
  CFG программы сохраняется. Память регистров типизирована (`i64`, `float`, `i1`).
  Флаги `fast-math` не используются.
- В режиме `--calls` для каждой инструкции, кроме управления потоком,
  генерируется один вызов функции. В `runtime.cpp` каждому коду операции
  соответствует отдельный экземпляр шаблонного эмулятора. Единый ABI передаёт
  биты float32, целые числа и указатели через аргументы типа i64. Операнды
  индексной адресации передаются как пара «база, индекс», поэтому доступ к памяти
  выполняет эмулятор. Загрузки и сохранения регистров и преобразования ABI
  генерирует слой доступа к операндам. `loop`, `br`, `jmp` и `halt` всегда
  преобразуются непосредственно в инструкции управления потоком IR.
- `engine.cpp` — запуск MCJIT через `ExecutionEngine` с явным сопоставлением
  символов графических функций и эмуляторов их адресам. Указатель на машинный код
  функции получается из движка. В сохраняемом IR используются символьные
  объявления, а не встроенные адреса функций текущего процесса.
- `simulator.cpp` — другая реализация того же интерфейса `Visitor`. Она хранит
  указатель текущей инструкции и изменяемые регистры и использует те же эмуляторы,
  что и режим `--calls`. Программа `asm_sim` не линкуется с библиотеками LLVM.
  Дополнительно она обнаруживает чтение неинициализированных регистров и выход
  за границы памяти, указывая строки исходного ASM.
- Для графики используются заглушки из `task_3/sim_stub.cpp`: без открытия окна
  проверяются порядок и координаты пикселей, диапазон цветов, полнота кадров
  и накопительные контрольные суммы.

Программа на ASM должна инициализировать регистры до чтения, соблюдать границы
памяти и предусловия преобразований из ISA.md. В сгенерированном IR неявной
инициализации регистров нет.

## Проверка

`task4_check` компилирует исходный `app_Os.ir`, ограничивая исполнение тремя
кадрами, и сравнивает полный вывод заглушек с обоими режимами Execution Engine
(с `--opt` и без него) и с чистым симулятором. `test_isa.py` также проверяет
циклическое переполнение целых чисел, знаковость, совпадение регистров-операндов,
условия-константы, заполнение диапазона нулевой длины, ограничение яркости,
раздельное округление умножения и сложения, управление потоком и диагностику
парсера во всех режимах исполнения. Эталон компилируется с `-O0`, чтобы сохранить
округление арифметических операций исходного IR.

| --- | ---: | --- |

| 2 | 2 359 296 | `7c3c891ae0faf7f9` |
| 3 | 3 538 944 | `66bca24457862d80` |
